## 1. 背景与问题

### 1.1 现状

索引层的来源区分**已经存在**。每篇文档记录有 `kind`，来源各自明确：

| `kind` | 判定依据 | 含义 |
|---|---|---|
| `upload` | 会话 `user/message` 的 `file` 块 | 用户在会话里发送的文件 |
| `image` | 会话 `user/message` 的 `image` 块 | 用户粘贴的图片 |
| `generated` | `tool/call` 命中 `writeTools`（默认 `write`/`edit`/`multi_edit`） | 会话生成或修改的文件 |
| `folder` | `root` 目录扫描，不归属会话 | 本地目录里的既有文件 |

判定位置：`sources/attachment-source.js:35-43`、`sources/session-source.js:40-41,191,209`、`sources/folder-source.js:62`。`kind` 已经进入面板数据（`index/aggregate.js:121`）、搜索结果（`search/rank.js:88`）和 `doc_list` 的渲染（`tools/list.js:4-8,63`）。

### 1.2 缺失

来源信息在三个地方没有被用起来：

1. **面板丢掉了来源。** `classify()` 除 `image` 外只看扩展名（`client.js:90-97`），"类型"列显示「文档 / 代码 / 文件」；类型筛选只有 全部 / 文档 / 代码 / 文件 / 图片（`client.js:656-662`）。用户无法从列表判断一篇文件是自己传的，还是 agent 写的。
2. **`doc_search` 不显示来源。** 结果行只有 `工作区 › 会话 › 路径:行号`（`tools/search.js:49`），结构化结果里有 `kind` 但模型看不到。"这是我传的资料，还是上轮生成的产物"恰好影响引用判断。
3. **同名字段承担两件事。** 「类型」既指扩展名又容易被理解成来源，语义重叠。

### 1.3 实测证据

- `demo.md`：本会话生成，`kind=generated`，面板与 `doc_list` 可见。
- `1.3.md`：用户上传，`kind=upload`，`key=attachment:sha256:6bde…`。
- `2.2.md`：用户刚上传，重建索引后应成为第二条 `upload`。
- `docs/` 下 962 篇：`kind=folder`，全部显示为「文档 / 文件」，与上面两类无法区分。

## 2. 目标与非目标

### 2.1 目标

1. 用户在看列表时，**一眼**分辨「用户上传 / 会话生成 / 本地目录」。
2. 用户能**按来源筛选**，并与现有类型筛选叠加。
3. 模型在 `doc_search` 的文本输出里能看到来源，从而决定引用方式。
4. 全链路只有一个事实源：服务端 `kind`；客户端不得按扩展名重新推断来源。

### 2.2 非目标

- 不改索引结构、`pathKey`、`contentHash`，不新增索引字段，不需要迁移或全量重建。
- 不新增模型工具；工具数量保持 4 个。
- 不做"同一内容的上传副本与生成副本合并提示"（见 §6，单独排期）。
- 不把"来源"做成可编辑标签（用户手动改名/归类）。

## 3. 用户故事

| # | 角色 | 故事 |
|---|---|---|
| U1 | 用户 | 我打开文档库，能立刻看出哪些文件是我上传的，哪些是 agent 生成的。 |
| U2 | 用户 | 我只想看自己传进会话的资料，能一键筛出「用户上传」。 |
| U3 | 用户 | 我找一份 agent 生成过的文档，能筛「会话生成」而不被 962 篇目录文档淹没。 |
| U4 | 模型 | 我搜到一条命中时，知道它是用户上传的原始材料还是生成产物，以决定是否需要读全文。 |

## 4. 功能需求

优先级：P1 = 本次交付；P2 = 同批可选；P3 = 后续。

### FR-1 面板显示来源（P1）

- 文档行在名称旁或"类型"列内显示来源标识，取值固定为：**用户上传 / 会话生成 / 本地目录**。
- `image` 归入「用户上传」，可用图标或后缀区分图片。
- 来源来自 `/doclib/tree` 返回的 `kind`，不重新推断。
- 标识必须同时存在于搜索状态的行，因为搜索结果的 `kind` 已由 `search/rank.js:88` 提供。

**验收**：`demo.md` 显示「会话生成」，`1.3.md` 显示「用户上传」，`docs/` 文档显示「本地目录」。

### FR-2 按来源筛选（P1）

- 工具栏新增来源筛选，选项：`全部来源 / 用户上传 / 会话生成 / 本地目录`。
- 与类型筛选**独立且可叠加**：两个条件为 AND。
- 筛选只作用于当前展示集合（目录树与搜索结果都适用）。
- 切回 `全部来源` 恢复原行为。
- 分组标题右侧的计数（`N 篇`、`N 个任务`）必须随筛选结果变化，不能显示筛选前的总数。

**验收**：选「用户上传」时只剩 upload/image 文档；选「会话生成」时 `demo.md` 在列；两筛叠加（用户上传 + 图片）只剩 `image`。

### FR-3 `doc_search` 输出来源（P1）

- 文本渲染每条结果带来源前缀，例如 `[上传]`、`[生成]`、`[目录]`。
- 结构化输出保持现有 `kind` 字段不变（已存在，`tools/search.js:31`），不新增字段。
- 不改变排序、`score`、`snippet`。

**验收**：调用 `doc_search` 搜 `demo`，命中行显示 `[生成]`；搜 `2.2`（重建后）显示 `[上传]`。

### FR-4 `doc_list` 标签对齐（P1）

- 现有 `kindLabel()`（`tools/list.js:4-8`）映射为：`生成 / 上传 / 图片 / 目录`。本次统一为与 FR-1 相同的三档文案，避免面板和工具各说一套。
- 保留"图片"信息时可写「用户上传（图片）」。

**验收**：同一篇文档在 `doc_list`、`doc_search`、面板三处来源文案一致。

### FR-5 筛选器可访问性（P2）

- 来源标识的完整含义通过 `title` 或 `aria-label` 暴露，不能只靠颜色区分。
- 来源筛选有 `aria-label`，与类型筛选的现有做法一致（`client.js:1080`）。

### FR-6 来源统计（P3）

- `doc_status` 已有 `uploads / generated / folder` 计数，面板状态行可展示为「上传 3 · 生成 1 · 目录 962」。
- 该项为顺手可做，不做也不影响验收。

## 5. 交互与文案规则

| 场景 | 文案 | 说明 |
|---|---|---|
| 来源列/标识 | 用户上传 / 会话生成 / 本地目录 | 三档固定词，不随筛选改写 |
| 筛选下拉 | 全部来源 / 用户上传 / 会话生成 / 本地目录 | 与标识同词 |
| 图片文档 | 用户上传（图片） | 类型列仍显示「图片」 |
| 空态（来源筛选无结果） | 当前来源下没有文档。 | 与现有类型空态并列，不合并成一句模糊提示 |

规则：

1. 面板不得出现「上传」与「用户上传」混用。
2. 来源标识不得依赖颜色单独传达（色觉可访问性）。
3. 搜索行与树行的来源标识位置一致，避免切换时跳动。

## 6. 语义边界与例外

1. **"生成"只认工具名。** `writeTools` 默认三个（`index.js:48`）；用 `apply_patch` 或 `bash` 重定向写出的文件不会记为 `generated`，只会以 `folder` 出现（`sources/session-source.js:40-41`）。本次不改判定，需求文档明确该限制；如需扩展列入 P2 决策。
2. **上传后再被编辑会产生两条记录。** 上传件身份是 `attachment:<id>`，写回工作区的文件是 `wb:<workspace>/<rel>`，是两份物理副本，两条记录符合模型。本次不做合并提示。
3. **目录扫描与会话写入撞同一路径时，来源以会话为准。** 合并逻辑优先保留非 `folder` 的 `kind`（`index/build-index.js:58`、`shared/doc-record.js:93-97`），因此一篇既在目录里又被 agent 写过的文件显示「会话生成」。
4. **旧索引兼容。** v2 迁移记录保留了原 `kind`（`shared/doc-record.js:150`）；不重建也能显示来源，只是正文搜索要等一次重建（现有行为，不受本次影响）。
5. **附件读取失败时仍保留记录**，来源显示不变，只是不可搜、不可读正文。

## 7. 非功能需求

| 项 | 要求 |
|---|---|
| 兼容性 | 不改协议字段；`/tree`、`/search` 的既有消费方不受影响 |
| 数据迁移 | 无。`kind` 已在索引中 |
| 性能 | 客户端只增加常数级映射，单次渲染增量可忽略 |
| 离线/失败 | 来源缺失（旧记录无 `kind`）时回退为「本地目录」，不得报错或隐藏文档 |
| 构建 | 只改 `client.js` 与 `tools/`，需要重建 Web 产物并在现有 GUI URL 刷新验证 |

## 9. 待拍板

1. **来源列形态**：单独一列，还是并入现有"类型"列（如「生成 · 文档」）？建议单独一列，类型列继续表达扩展名维度，避免再次混用。
2. **`image` 是否单列**：并入「用户上传」还是独立「用户上传（图片）」档？建议并入，图片用类型列区分。
3. **`writeTools` 是否扩展**：把 `apply_patch`/`bash` 纳入"生成"判定会让来源更准，但 `bash` 无法可靠推断写目标，建议本次不扩，只在文档里写明限制。
