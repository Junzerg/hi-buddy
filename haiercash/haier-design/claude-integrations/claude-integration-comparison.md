# Claude 集成路线比较与建议

## 当前决定

采用方案一：使用本机 Claude Code，由独立插件提供 app 内会话入口。宿主接入与验收约定见[宿主接入设计](host-integration-design.md)。下文保留选型时的比较与原始建议，不作为当前实施路线。

## 摘要

建议将 **DSH 原生 agent 能力与 Claude Code 常见工作流兼容作为产品主线（方案二）**，将 **原生 Claude 执行作为可选入口（方案一）**。这个建议以 hi-buddy 的桌面与内网分发定位为前提：长期需要自主选择模型、接入企业工具并维护统一权限和会话体验。如果首要验收条件是现有 Claude Code 用户立即获得原生执行效果，应反过来先做方案一。两条路线都已有可复用代码，但目前都不能承诺“无缝迁移”。

以下比较保留选型依据，不代表功能已经实现。事实依据、调查方法和限制见[调研记录](claude-integration-evidence.md)。

## 范围与术语

这里将需求理解为：在 hi-buddy 桌面 app 中提供代码仓库探索、规划、编辑、命令执行、验证、持续对话和工具扩展的 agent 工作流。用户提到的 Claude Desktop 是体验参照，Claude Code 是拟复用或兼容的执行系统。

Claude Desktop 的聊天、Cowork、Code 工作区与 Claude Code CLI 不是同一个可嵌入组件。官方桌面文档包含 diff、预览、并行工作区等桌面能力；接入 CLI 或 SDK 不能直接获得整套界面。完整 Cowork、电脑操作、云会话和跨设备同步不计入本次推荐的首期范围，若它们是核心目标，需要重新比较。[官方桌面文档](https://code.claude.com/docs/en/desktop)

“Claude 插件”也需要区分：本建议中的方案一是 **DSH 插件驱动 Claude 执行器**；安装到 Claude Code 内部的插件则是另一种扩展机制。只把 Claude 模型接入 DSH，仍属于方案二，因为 agent 循环由 DSH 控制。

## 当前产品基础

源码检查说明两条路线都不是从零开始，但包存在不代表当前安装已启用或已通过桌面验收。

| 已有基础 | 对决策的影响 |
|---|---|
| Electron → Desktop Host → DSH Web 应用的运行架构 | 可保留现有桌面壳和业务入口，不必另做整套应用 |
| 原生 agent loop、工具执行、审批、持久化、压缩、子代理、技能和 MCP 能力 | 方案二主要工作是配置兼容、交互补齐与效果验证 |
| `subagent-claude-code`，依赖官方 Agent SDK | 方案一可参考其进程管理与失败处理，但不能直接当持续聊天后端 |
| 项目指令支持 `AGENTS.md`、`CLAUDE.md` 及对应 local 文件 | 已有指令迁移基础，仍需验证加载顺序和其他 Claude 配置语义 |
| 实验性 Claude hooks／mods 兼容包 | 可复用已覆盖子集，不能宣称整个 Claude 插件生态兼容 |

特别注意：现有 Claude 子代理使用固定 SDK 平台运行时，**不会回退到本机 `claude`**；每次任务是独立执行，关闭产品会话持久化，返回最终结果，不提供续聊、进度流和人工审批。详见[现有插件说明](../../../packages/subagent/subagent-claude-code/README.md)及[调研证据](claude-integration-evidence.md#本地证据)。

## 路线比较

下表是基于架构与需求的工程判断，不是性能测试结果。方案一按“完整嵌入会话 UI”评估，而非仅启动外部终端。

| 维度 | 方案一：Claude 执行，app 提供 UI | 方案二：DSH 执行，兼容常见工作流 |
|---|---|---|
| 原生 agent 行为 | 最接近原生；仍受 SDK、版本和配置差异影响 | 行为由 DSH、模型和提示共同决定，无法承诺等价 |
| 首个可用版本 | 只委派任务较快；完整聊天仍需流式、审批和恢复集成 | 基础能力已在仓库；先覆盖常见闭环较合适 |
| 用户已有资产 | 更容易复用原生指令、技能、hooks 和设置；需固定加载策略 | 逐项导入与诊断；复杂插件和旧会话迁移成本较高 |
| 内网运行 | 需可达的受支持 Claude 服务、凭据与运行时分发条件 | 可选择获准的内网模型或网关；效果取决于实际模型 |
| 模型与供应商选择 | 保留 Claude 执行系统支持的模型服务边界 | 可复用 DSH 模型适配层，选择空间更大 |
| 企业工具集成 | 优先通过 MCP 暴露；DSH 内部工具不会自动变成 Claude 工具 | 原生插件、工具与业务权限较容易统一 |
| 权限与审计 | Claude 原生工具不经过 DSH 工具流水线，需要专门接线 | DSH 掌握工具审批与事件记录；仍需验证插件旁路和操作系统限制 |
| 会话与恢复 | Claude 保存执行上下文，app 保存引用和展示；需明确双侧职责 | 可沿用 DSH 日志和恢复体系，但不直接读取原生 Claude 会话 |
| 长期维护 | 跟随 CLI／SDK 协议和版本升级；完整 UI 适配持续付费 | 自己承担 agent 质量与兼容子集维护；应避免追逐所有原生细节 |
| 成本 | Claude 用量加适配维护；当前委派模式还可能产生父 agent 用量 | 可选择模型成本，但失败重试、上下文和人工返工可能抵消单价优势 |
| 产品定位 | 为已使用 Claude 的用户提供桌面入口 | 企业自己的 agent 工作台，降低迁移学习成本 |

**选择依据：**当前仓库的桌面与内网定位、已有 DSH 投入，使方案二更适合作为默认主线。若用户群几乎全部已有 Claude 环境、可使用其服务，且原生插件兼容优先于内网自主性，方案一更有优势。纯内网无法访问获准 Claude 服务时，“本机装了 CLI”不能让方案一离线推理。

## 方案一的落地边界

建议把“外部终端启动器”“现有一次性子代理”“可交互的原生执行会话”作为不同交付等级。用户所描述的 app 内 UI 入口若包含连续聊天，应按第三种设计。

建议的数据流是：**现有桌面 UI → DSH Host 中的执行适配器 → Claude CLI／Agent SDK → Claude 工具和模型服务**。同一顶层会话只由 Claude 管理执行循环；DSH 负责入口、交互与展示。若只是让 DSH 主 agent 调用现有 Claude 子代理，用户实际得到的是双层委派，不能视为同一体验。

完整入口至少需要：

1. **运行时选择。**本机 CLI 和 SDK 固定运行时是两项独立选择。用户路径需检测可执行性、版本与所需能力；固定运行时便于回归，但增加分发管理。当前插件实现的是后者，改成优先本机 CLI 属于新增行为。不能在失败时静默切换版本或账号环境。
2. **结构化交互。**使用官方程序化接口处理消息、工具状态、审批、用户问题和取消；不要解析终端文字来推断状态。CLI `-p` 适合自动化，完整 UI 优先评估 SDK 的审批回调。[程序化调用](https://code.claude.com/docs/en/headless)、[权限接口](https://code.claude.com/docs/en/agent-sdk/permissions)
3. **会话归属。**保存执行器类型、版本和原生会话 ID；Claude 上下文是续聊依据，DSH 展示记录不能冒充原生上下文。崩溃后恢复须先核对状态，不自动重跑结果未知的写操作。
4. **工具授权。**Claude 内置文件和 shell 工具不自动受 DSH `tools/pre-execute` 管辖。审批 UI 需接入原生决策路径，DSH 自有业务工具可通过受控 MCP 接入；操作系统隔离另行验证。
5. **退出与升级。**覆盖取消后子进程清理、Windows／macOS 差异、错误展示、CLI 缺失、版本不支持、登录失效，以及升级后的兼容性回归。

官方文档区分“用户在未修改的 Claude Code 中自行登录”与“第三方 app 提供 Claude 登录或中转订阅凭据”。不能把“已安装并登录”直接当作本产品可自由复用订阅的依据；应按最终分发、调用和计费模式核对适用要求，app 不提取或代存原生会话令牌。[官方产品集成与凭据说明](https://code.claude.com/docs/en/legal-and-compliance)

这条路线保留原生能力，但 app 依旧需要维护桌面体验。SDK 提供执行能力，不提供现成的 Claude Desktop 界面。[Agent SDK 概览](https://code.claude.com/docs/en/agent-sdk/overview)

## 方案二的迁移目标

将“无缝迁移”拆成可验收的兼容等级：先让用户熟悉的工作闭环成立，再迁移常用资产；不把命令名称相同视为行为相同。

| 目标 | 当前基础 | 建议承诺 |
|---|---|---|
| 浏览仓库 → 修改 → 执行测试 → 查看结果 | DSH loop、文件／shell 工具、会话 UI | 首期优先，使用真实项目验证任务完成率 |
| 规划 → 审阅 → 执行 | `plan-mode` 与审批 UI | 首期优先；计划模式自身仍暴露工具，强制只读必须由策略实现 |
| 项目指令 | 已支持 `CLAUDE.md` 候选文件 | 检查优先级、嵌套范围、local 覆盖和预算，明确差异 |
| 常用 skills 和快捷命令 | 技能发现、加载及 UI | `.claude/skills` 不是当前默认发现根；支持导入或配置，并报告不支持字段 |
| MCP 工具 | 已有 MCP client 与资源包 | 验证配置格式、环境变量、认证、错误和交互，不直接复用全部原生设置 |
| 子代理与长任务 | DSH 子代理及上下文压缩 | 验证任务分解、取消、结果汇总与上下文保真 |
| hooks／mods | 已有实验性兼容桥 | 仅承诺白名单子集；未知配置显式提示，避免静默失效 |
| 会话恢复 | DSH 持久化与恢复 | 保证 DSH 会话连续性；原生历史导入和跨引擎续聊另行设计 |
| 文件回退、worktree、diff | 存在相关基础，但完整桌面闭环未验证 | 单独验收；日志 checkpoint 不等于文件改动撤销 |

方案二的主要风险是**效果差距**：相同模型也会因上下文、工具描述、恢复机制不同而产生不同表现；换用内网模型还会引入模型能力差异。首期应选定模型和任务集，避免同时承诺“全模型适配”和“原生体验等价”。

迁移流程建议先扫描项目资产，输出“可直接使用／需要映射／暂不支持”清单，由用户选择启用。原有文件保持原样；未经确认不自动执行导入 hooks，也不把 Claude 权限配置机械映射成 DSH 放行规则。

## 建议的实施顺序

推荐按单一主线推进，每阶段都依据可观察结果决定是否继续，避免同时建设两套完整产品。

1. **确定基准与兼容清单。**收集代表性项目的 Claude 资产和高频工作流，明确可达模型服务及目标操作系统。用现有原生子代理做有限任务对照时，标注其无人值守限制，不能据此评价完整交互体验。
2. **交付 DSH 迁移 MVP。**优先完成指令、技能、MCP 的可解释导入，以及规划、编辑、测试、审批、取消和恢复闭环。先复用现有插件，只补影响验收的缺口。
3. **按需求增加原生执行入口。**只有实际用户依赖原生能力，且部署与认证条件满足，才投入完整 Claude 会话适配。保留现有一次性子代理用途，持续会话另设清晰入口。
4. **用评测决定扩展。**如果 DSH 的效果差距阻碍主要任务，先调整模型和执行策略；若仍不满足，提升原生入口优先级。不要以外观相似替代任务效果。

双引擎情况下，用户在新建会话时明确选择执行器；切换执行器创建新会话，可携带明确标注的摘要，但不宣称保留完整执行状态。只有真实需要同时维护两个入口时，才抽取共享启动、流式展示、审批、取消与恢复接口。

## 验证与投入判断

投入仅做相对判断，尚无团队规模、真实用户资产和性能样本，不能可靠给出工期或节省比例。

| 交付范围 | 相对投入 | 最大不确定性 |
|---|---|---|
| 外部 CLI 启动或现有一次性委派入口 | 小 | 安装、认证和目标平台可用性 |
| 方案一：完整 app 内 Claude 会话 | 中到大 | 双向交互、续聊、退出清理、原生版本兼容 |
| 方案二：常见工作流与资产迁移 MVP | 中 | 目标模型效果、配置差异、现有 UI 的实际缺口 |
| 方案二：完整复刻 Claude Code／Desktop | 很大且持续变化 | 闭源行为、快速变化的生态、产品范围无限扩大 |

建议在同一批项目、相同初始提交和相近任务预算下比较两条路线。模型可一致时先做同模型对照；不能一致时，分别报告“整体产品效果”和“模型差异”，不将所有差距归因于 harness。

验收至少覆盖：

- 解释仓库、修复带测试的缺陷、跨文件修改、执行测试、MCP 查询、技能调用、拒绝写入、取消长命令、重启续聊、缺失凭据，以及有未提交改动的工作区。
- 通过外部测试和实际文件差异判定完成；记录用户介入次数、首次有效反馈时间、总耗时、模型用量、失败恢复情况。报告中位数与尾部，不只展示最好案例。
- 安全约束作为硬条件：被拒绝的动作不执行、计划只读承诺有强制措施、取消后无失控子进程、恢复不重复未知副作用、用户原有改动不被覆盖。
- Windows 与 macOS 的真实桌面入口分别验证；内网连通性由有权限的用户在目标环境验证。

评测通过后再确定产品措辞：可以承诺经验证的工作流与资产兼容范围；“完全无缝替换 Claude Code”不作为本次可交付结论。

## Dev Note

待产品确认的选择：首批用户是否必须使用已有 Claude 订阅、内网是否允许访问获准 Claude 服务、最重要的三类工作流、以及是否包含 Cowork／电脑操作。
